# 08 · 踩坑记(二):协议、TLS 与传输

这一篇是**传输内核**相关的坑:协议、TLS、异步运行时、落盘与事件。

---

## 坑 1:加密传输 100% 收到 0 字节——TLS 1.3 的收尾陷阱

**现象**:明文传输完全正常;只要开启加密,**iPhone / 开加密的 Mac 发给 Android,
接收端收到的字节数恒为 0**,状态 "transfer incomplete"。

**排查过程**:写一个用**真实协议**的最小发送端(而不是手工拼字节)对着 Android 发,
抓 Android 端日志:

```
receiver: awaiting data connections
DataOpen session ... found in pending
... TLS handshake ok ...
drain ended: done=0 total=307200 complete=false
```

握手成功、数据一个字节没到。再看发送端:它明明把 307200 字节"写成功"了。

**根因**:

- TLS 1.3 服务端在握手后会自动发送 `NewSessionTicket` 等**握手后记录**;
- 发送端发完数据后**只写不读**,从没读取对端的任何数据,直接关闭 socket;
- 内核发现接收缓冲区里还有未读数据就关闭 → 发 **RST**;
- 接收端 TCP 收到 RST 后会**丢弃已缓冲的应用数据**,应用层 `read` 直接得到
  `ECONNRESET`——于是"握手成功、数据全丢"。

**修复**:发送端在关闭前,先发 `close_notify`,再把对端记录**读到 EOF**,
让连接优雅关闭(发 FIN 而不是 RST):

```rust
let _ = tls.shutdown().await;
let mut sink = [0u8; 4096];
loop {
    match tls.read(&mut sink).await { Ok(0) | Err(_) => break, Ok(_) => continue }
}
```

**教训**:
- **TLS 连接必须"双向收尾"**;只写不读地关闭会触发 RST,且**只在加密路径**出现;
- 表现为 0 字节时,很容易误判成"接收端写文件失败";**要看协议时序,而不是猜**;
- 本机回环测试(`v3_secure_transfer`)能复现——**早该让这个测试保持绿色**,
  而不是把它当作"环境性失败"忽略掉(见坑 7)。

## 坑 2:事件 `kind` 大小写——原生端全部解析失败

**现象**:iOS/Android 上事件(进度、请求、完成)解析不出来,UI 一直不动。

**根因**:`TransferEvent` 用 serde 的**内部 tag** 序列化,tag 值默认是**枚举变体名**:

```rust
#[serde(tag = "kind")]
pub enum TransferEvent { Request { .. }, Progress { .. }, Finished { .. }, Recorded(..) }
```

即 `"kind":"Request"`(大写)。原生端一开始按 `"request"` 小写匹配 → 全部落空。

**修复**:原生端严格匹配**大写**的 `kind`。

**教训**:跨语言(serde JSON ↔ Swift/Kotlin)时,**枚举 tag 的大小写是契约的一部分**。
要么统一约定,要么在序列化端显式 `rename_all`。**用真实序列化器的输出对一遍**。

## 坑 3:原生动 `tokio::spawn` → panic → 直接 SIGABRT

**现象**:Android/iOS 点发送,App 直接崩溃(SIGABRT)。

**根因**:`start_send` 内部会 `tokio::spawn`,这**必须在 Tokio 运行时上下文里调用**。
桌面端命令是 async(跑在 Tauri 的 Tokio 运行时里)所以没事;
原生端从 JNI/FFI 线程直接调用时没有运行时上下文 → `tokio::spawn` panic → 崩溃。

**修复**:在调用 `start_send` 前显式进入运行时:

```rust
let _guard = c.runtime.enter();   // 再调用 start_send
c.sessions.start_send(peer, files, cfg, secure, verify)
```

**教训**:`tokio::spawn` 不是"随便哪都能调"的。**跨越 FFI/JNI 边界回到内核时,
要显式建立运行时上下文**。

## 坑 4:v2 发送端配 v1 接收端 = 不兼容

**现象**:新版发送、旧版接收,大文件传不动。

**根因**:v2 的发送端对一个大文件会开**多条数据连接**(按偏移切段),
而 v1 的接收端**只接受一条**数据连接。协议帧没变,但**会话层行为变了**。

**修复/策略**:项目选择"大家一起升级",并在协议里保留 `proto_ver` 做闸门;
不做自动降级。

**教训**:**"帧格式没变"不代表"协议没变"**。会话/连接模型也是协议的一部分,
版本号要覆盖到行为层面。

## 坑 5:手工拼 postcard 做探针,结果自己把自己坑了

**现象**:为了定位坑 1,手写了一个 Python 探针发 `Hello`;Android 读到了首帧却
不回复 `HelloAck`,日志显示 `early eof`。

**根因**:**手工编码 postcard 是对的难度**——`Uuid` 的序列化、枚举判别式、
变长整数……错一个字节,接收端 `from_bytes` 就失败,连接被丢弃。
那次的失败其实是**探针的错**,不是产品的错。

**修复**:改用**真实协议代码**写探针(调用内核的 `run_sender`),而不是手拼字节。

**教训**:**调试协议问题时,用真实序列化器构造数据**;手拼字节只会在
"到底是产品坏了还是探针坏了"上浪费时间。

## 坑 6:接收端不做自动重试(避免进度翻倍)

**现象/决定**:数据连接失败时,最初想做自动重试。

**根因**:重试会把**整个 bucket 重发**,而接收端是按收到字节**累加**进度的,
于是完成判定会错乱(重复计数)。

**决定**:失败即止,不自动重试——局域网稳定,单连接失败概率低;失败交给用户决定是否重发。

**教训**:在有"接收端按字节累加"的模型里,**重试不是免费的**;
要么做幂等(按 offset 去重),要么不重试。

## 坑 7:被当成"环境问题"忽略的失败测试,其实是真 bug

**现象**:`v3_secure_transfer` 长期失败,被记录为"本机环境性失败,可忽略"。

**真相**:它就是坑 1(TLS 收尾 RST)。修复后,该测试**从超时变为通过**。

**教训**:一个稳定的、可复现的失败测试,**不要轻易归因于环境**。
"忽略红灯"会让真实缺陷长期潜伏;**红了就先修或先查**。

---

## 坑 8:原生端历史一直是空的

**现象**:iOS/Android 传完了,但历史列表没有记录。

**根因**:桌面端在 `run()` 里把 `Recorded` 事件写进历史;**原生引擎没有这段逻辑**,
于是事件发了、历史却没落库,`Finished` 时再刷新历史会覆盖成空。

**修复**:原生引擎在收到 `Recorded` 时也 `history.append`,与桌面一致。

**教训**:**共享内核里"只有桌面才做"的副作用,移动端会缺**。抽内核时要把
这类"旁路副作用"一起搬过来。

---

## 坑 9:加密模式用不了 `sendfile`

**现象**:开启加密后吞吐下降。

**根因**:`sendfile` 只能把文件字节直接推给**裸 socket 的 fd**,
无法穿过 TLS 层。所以加密模式必须回退到 `pread` + `write`。

**决定**:接受这个代价——**安全模式是"可选"的**,默认明文仍然走最快路径。

**教训**:性能优化与安全层常常互斥;**把它们做成可切换的两条路径**,而不是
强行统一。
