# 09 · 踩坑记(三):UI、构建与发布

这一篇是**界面、工程配置、打包安装**以及**协作流程**上的坑。

---

## 坑 1:iOS 选不了相册——`.fileImporter` 根本看不到相册

**现象**:iOS 上点"选择文件",只能选文件 App 里的内容,**相册里的照片视频选不了**。

**根因**:`.fileImporter` 走的是系统**文件**选择器(UIDocumentPicker),
它**本来就不提供相册入口**——相册不是"文件"。这不是 bug,是用错了工具。

**修复**:增加"从相册选择"入口,改用 `PhotosPicker`(跨进程选择,**不需要相册权限**),
选中的项写入临时文件后发送:

```swift
.photosPicker(isPresented: $showPhotoPicker, selection: $photoItems,
              maxSelectionCount: 30, matching: .any(of: [.images, .videos]))
```

**教训**:**"文件"和"相册"在 iOS 上是两个不同的世界**。要覆盖用户预期,
得两个入口都给。

---

## 坑 2:二维码模糊

**现象**:iOS/Android 上的二维码"糊",扫码距离受限。

**根因**:两点——**分辨率偏低**(512 被放大到显示尺寸),以及**用了双线性缩放**
(把黑白相间的模块"插值"成灰边)。

**修复**:
- 生成端提到 **1024**;
- 显示端关闭平滑:iOS 用 `.interpolation(.none)`,Android 用
  `BitmapPainter(filterQuality = FilterQuality.None)`(最近邻)。

**教训**:二维码/像素图**必须"最近邻"显示**,且显示尺寸不要超过位图分辨率。

---

## 坑 3:桌面改名"看起来对,其实后端是空实现"

**现象**:桌面上改显示名,界面显示已保存,但实际没生效。

**根因**:Tauri 命令 `set_display_name` 是**占位空实现**(直接 `Ok(())`),
前端调用成功、后端什么都没做。另外,发现层的 `set_display_name` 也是 no-op,
即使本地改名了,广播出去的名字也不变。

**修复**:命令真正更新内存身份、写 `identity.json`,并让发现层**重新广播**;
各平台发现后端(桌面 mDNS、iOS Bonjour、Android NsdManager)都补上重注册。

**教训**:**"界面看起来对了"不等于"功能生效"**。要把动作一路追到持久化和
对外可见(别的设备能否看到新名字),否则只是改了内存里的一个字符串。

---

## 坑 4:Material 控件的"度量"细节

**现象**:Android 设置页三个步进器的 `− / +` **不在同一列**(数值宽度不一);
发送栏的"加密/SHA-256"开关**过高**,与设计不符。

**根因**:步进器数值区宽度随内容变化,导致两侧按钮错位;Material 的 `Switch`
触摸目标有最小高度,塞进小控件会显得很高。

**修复**:
- 步进器改成**一体分段式**、数值区**固定宽度**,保证按钮对齐;
- 开关改成**自绘紧凑开关**(`Surface` + `Box`),主动控制高度。

**教训**:系统控件有自己的一套度量(最小触摸目标、内边距)。
**要精确对齐时,要么约束父容器,要么自绘**。

---

## 坑 5:点空白取消选中,和设备按钮打架

**现象**:雷达页点空白要"取消选中",但设备本身也是可点按钮——两者手势冲突。

**根因**:如果把"取消选中"的手势挂在**父容器**上,点设备时父容器也可能收到
同一个点击,导致"刚选中又被取消"。

**修复**:
- iOS:在 `ZStack` **最底层**放一个透明点击层,设备按钮在上层,按钮优先消费点击;
- Compose:父容器 `pointerInput { detectTapGestures }` + 子节点 `clickable`,
  子节点消费后父层不再触发。

**教训**:**手势冲突要靠"层级/命中区域"解决**,不要靠时序。

---

## 坑 6:设计系统与深浅色

**现象**:深色好看、切到浅色就"发灰、对比不足";反复改 UI 却总被否。

**根因**:颜色一开始是**硬编码的深色值**(白透明度、固定灰),没有随主题切换;
以及**没有先定原型就写代码**,来回返工。

**修复**:
- 用 **动态色**(`UIColor { trait in … }` / `Color(UIColor{…})`)让色板随深浅色切换;
- 光晕/扫描/阴影等透明度按 `colorScheme` 给不同值;
- **先用单页 HTML 原型定稿视觉,再落 SwiftUI/Compose**。

**教训**:**先原型、后实现**。视觉方向没定就写原生代码,返工成本极高。

---

## 坑 7:`xcodegen` 与工程文件

**现象**:新增 Swift 文件后编译报 `cannot find X in scope`。

**根因**:Xcode 工程是从 `project.yml` **生成**的;新增文件后没有重新生成,
文件没进工程。

**修复**:改 `project.yml`、新增 Swift 文件后,进入 `gen/apple/` 执行
`xcodegen generate`。**不要手改 `project.pbxproj`**(会被覆盖)。

**教训**:**生成物不要手改**;把"生成工程"作为流程的一步。

---

## 坑 8:千万别 `pnpm tauri android init`

**现象(风险)**:一旦运行,会**重新生成 Tauri 的 Android 工程**,覆盖掉原生
Compose/JNI/Gradle 配置。

**修复/流程**:Android 已是原生工程,构建只走 `build-android.sh` + Gradle;
**不要跑 init**。

**教训**:**模板化脚手架会重写目录**;原生替换过的工程要"锁住入口"。

---

## 坑 9:装包失败不是代码问题

**现象**:
- Android `adb install` 报 `Failure [-99]`;
- iOS `devicectl install` 报 `4016 (unavailable)` / `4000 (connection could not be established)`。

**根因**:设备**锁屏/休眠**;或连接不稳定。

**修复**:
- Android:先 `adb shell input keyevent KEYCODE_WAKEUP`;
- iOS:**解锁并保持亮屏**,必要时先 `uninstall` 再装;
- 连接断开就重试。

**教训**:真机部署的失败常常发生在"设备状态",而不是代码。**先排除设备状态,
别一上来就怀疑构建**。

---

## 坑 10:Tauri 权限与窗口标签

**现象**:新增前端调用某个能力时报"不允许"。

**根因**:Tauri 2 是**能力(capability)白名单**模型;插件命令需要在
`capabilities/*.json` 里授权,且 `windows` 列表要包含实际窗口标签(`main`)。

**修复**:在 `capabilities/default.json` 增加对应权限(`core:default`、
`opener:default`、`dialog:default` 等),窗口标签保持一致。

**教训**:**"命令没注册/没授权"在运行时是静默失败**;新增能力要同时改
Rust 的 `generate_handler!` 与前端调用与 capability。

---

## 坑 11:平台默认值也会影响体验

**现象**:iOS 的"加密传输"默认是开的,导致很多本该走明文(更快)的传输
默认走了 TLS,还"顺带"暴露了 TLS 的坑。

**修复**:把 iOS 默认改为**不加密**,与其它端一致。

**教训**:**默认值就是产品行为**。跨端要统一默认,避免"同一次操作在不同端
表现不同"。

---

## 小结

| 类别 | 坑 | 对策 |
|------|----|------|
| 平台 API | fileImporter 看不到相册 | 该用 `PhotosPicker` 用 `PhotosPicker` |
| 渲染 | 二维码模糊 | 高分辨率 + 最近邻 |
| 前后端 | 改名是空实现 | 追到持久化与对外可见 |
| 度量 | 步进器错位 / 开关过高 | 约束度量或自绘控件 |
| 手势 | 点空白 vs 点按钮 | 层级/命中区域解决 |
| 主题 | 硬编码深色 | 动态色 + **先原型** |
| 工程 | xcodegen / android init | 生成物不手改;模板不重跑 |
| 部署 | 安装失败 | 先看设备状态(锁屏/连接) |
| Tauri | 权限/窗口标签 | capability 与 handler 同步 |
| 产品 | 默认值不一致 | 跨端统一默认 |
