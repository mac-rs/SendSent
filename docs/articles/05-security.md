# 05 · 安全与校验:可选加密 + 完整性校验

## 默认是明文,加密是可选项

设计上刻意**不默认加密**:局域网传输的主要诉求是速度,而 TLS 会带来额外开销,
并且会让"零拷贝 sendfile"失效(见性能篇)。所以:

- 默认:明文 + 零拷贝,追求速度;
- 每次发送可勾选**加密传输**(TLS)与 **SHA-256 校验**。

接收端会回一个 `secure_ok`,只有双方都支持时才真正走 TLS:

```rust
let is_secure = secure && ack.secure_ok;   // 发送端
```

## TLS 层:rustls + 自签证书

证书在首次启动时用 `rcgen` 生成并持久化,纯 Rust、无系统依赖,移动端也能用:

```
<data_dir>/tls/cert.pem
<data_dir>/tls/key.pem
```

- 服务端:`rustls::ServerConfig` + 自签 ECDSA 证书;
- 客户端:**自定义校验器 `NoVerify`**——不做 CA 链验证。

为什么允许 `NoVerify`?因为证书是自签的、每台设备都不一样,没有公共 CA;
真实身份认证交给应用层的 PIN(设计意图)。这带来一个明确的安全边界:

> 当前实现里,加密能防住**被动偷听**(局域网嗅探),但**不能防主动中间人**——
> 中间人可以替换自签证书,客户端也不会拒绝。

## PIN 配对:设计意图与当前状态

设计中的流程是:发送端生成 6 位随机 PIN 并显示,接收端**由用户输入**同一个 PIN 回传,
双方比对一致才继续——这样即使有中间人,也需要知道 PIN 才能完成握手。

握手(安全模式)长这样:

```
控制连接 TCP(明文)
  发送端 ── Hello{ secure:true } ─────────────▶ 接收端
  发送端 ◀──────────── HelloAck{ secure_ok:true }
  ── 双方把这条控制连接升级为 TLS ──
  发送端 ── PinCode{ pin } ───────────────────▶ 接收端
  发送端 ◀──────────────── PinCode{ pin } ───── (用户输入)
  比对 → 一致:Manifest;不一致:Error、断开
```

> **现状说明**:接收端目前是把收到的 PIN **原样回传**(即"自动通过"),用户输入
> PIN 的交互是待完成项。因此加密的价值目前等同于"防偷听"。这是有意的取舍,
> 真正的认证能力会随着 PIN 输入交互补齐。

## 数据连接也要加密

安全模式下,**每一条数据连接**(不是一个文件一条,而是"桶"级)在发送
`DataOpen`(明文)之后,也各自升级为 TLS,之后的文件数据帧都在 TLS 里传。

```
数据连接:  明文 DataOpen{ session_id }  →  升级 TLS  →  数据帧(加密)
```

`DataOpen` 之所以留明文,是因为接收端要用它把"这条连接属于哪个会话"先认出来,
再决定用哪套 TLS 配置去 accept。同时,这个帧头本身不携带文件内容,泄露面很小。

## 一个真实的血案:加密传输收到 0 字节

安全模式上线后出现过一个"100% 失败"的现象:**iPhone/开加密的 Mac 发给 Android,
接收端收到的字节数是 0**。明文完全正常。根因与修复见踩坑篇,这里先给结论:

> **TLS 1.3 服务端在握手后会发 `NewSessionTicket`。发送端发完数据就关 socket、
> 却从没读过对端的任何数据,内核于是发 RST;接收端收到 RST 后会丢弃已缓冲的
> 应用数据——于是"成功握手、数据全丢",表现就是 0 字节。**

修复:发送端在关闭前先把对端记录读到 EOF(优雅关闭,发 FIN 而非 RST)。
这个问题"只有在加密路径"才出现,明文没有握手后记录,所以极易被误判成"接收端写文件失败"。

## SHA-256 校验

勾选校验后,发送端在数据发完后,通过控制连接发送 `VerifyInfo`:

```rust
VerifyInfo { hashes: Vec<(Uuid /*file_id*/, String /*sha256 hex*/)> }
```

接收端逐文件重新计算 SHA-256 并比对:

- 全部一致 → `Complete`,文件落盘;
- 有任何不一致或读取失败 → 标记失败,接收端不认为传输成功。

校验是**逐文件**的,所以即使多连接并行、乱序落盘,校验也只看最终文件内容,
与传输路径无关。

## 小结

- **速度与安全分离**:默认明文追求速度,加密/校验按次可选;
- **TLS 用纯 Rust**:证书自签、`NoVerify`,保证移动端可编译、易部署;
- **认证靠 PIN**(待补齐用户输入);
- **完整性靠 SHA-256**:逐文件、与传输路径解耦;
- **踩过的坑提醒我们**:加密路径的收尾(TLS 关闭语义)和明文完全是两回事。
